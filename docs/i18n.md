# Nappa — Localisation (i18n) plan

**Status:** English only today. Goal: be able to add French, German, Spanish and Chinese (Simplified) later by adding translation files, with no screen rewrites. The work now is the foundation; translating comes in M6.

Expo reference (SDK 58): https://docs.expo.dev/guides/localization.md and https://docs.expo.dev/versions/v58.0.0/sdk/localization.md. Re-check them before touching setup; Expo changes between SDKs.

## Decisions

| Topic | Decision | Why |
|---|---|---|
| Translation library | `i18next` + `react-i18next` | Plurals via `Intl.PluralRules` (needed for French, Russian, etc.), typed keys, context, works with translation tools. Lingui is the alternative if we later want extracted messages. |
| Device language | `expo-localization` (`getLocales`, `useLocales`, `useCalendars`) | The Expo-recommended way. |
| Dates, numbers, units, lists | Native `Intl` (Hermes), wrapped in `app/src/lib/format.ts` | Never translate these by hand; the library does not need to know about them. |
| Language choice | Follow the device. Per-app language comes from OS settings via the `expo-localization` config plugin `supportedLocales`. No in-app language picker in v1. | Expo guidance; less UI to build and test. |
| Units, 12/24h clock, diaper vs nappy | User **settings** with defaults from the device region. They are separate from language. | A French parent may want oz; a UK English parent says "nappy", a US one "diaper". Already planned in M1. |
| Source language | `en`. Missing keys in other languages fall back to `en`. | Never show a raw key or a blank. |
| RTL | Not in scope (all target languages are LTR) but code must not block it: logical spacing, no hard-coded left/right. | Cheap now, costly to retrofit. |

## Rules for code (summary; the binding copy is in `CLAUDE.md` and `app/AGENTS.md`)

1. No user-facing string literals in components. Every visible string, accessibility label, alert, placeholder and notification text goes through `t()`.
2. No building sentences by concatenation. Use whole sentences with `{{placeholders}}`; word order differs by language.
3. Plurals use i18next plural keys (`_one`, `_other`, plus others a language needs), never `count === 1 ? ... : ...`.
4. Data layers hold **raw values** (ISO timestamps, milliseconds, ml, grams) and the UI formats them at render time. `app/src/data/home.ts` currently stores pre-formatted strings (`'2h 10m'`, `'Window until 2:10 pm'`); convert it before wiring real data.
5. Format through `lib/format.ts` (duration, time of day, date, volume, weight, relative time), never `toFixed`, `toLocaleString` or string maths scattered in components.
6. Layouts must survive text about 40% longer than English (German) and tall glyphs (Chinese). No fixed-width text containers; allow wrapping; test with the longest string.
7. Use logical spacing and alignment (`ms-`/`me-`/`ps-`/`pe-`, `start`/`end`), not left/right.
8. Store IDs and enum values in data, never display text. The API returns data and error **codes**, not sentences meant for display.
9. New strings go into `en` only, with a short translator note when meaning is not obvious ("Feed" as noun or verb?). Other languages are added in batches, not per feature.

## Layout

```
app/src/i18n/
  index.ts            # i18next instance, device language, fallback to en, foreground re-read
  resources.ts        # bundles every locale's JSON; add a language here
  i18next.d.ts        # typed keys from the en resources
  locales/
    en/common.json    # shared: actions, units labels, errors
    en/home.json      # one file per feature/screen area
    ...
app/src/lib/format.ts # Intl wrappers
```

Later languages add `locales/fr/`, `locales/de/`, `locales/es/`, `locales/zh-Hans/` with the same file names. A small script (`npm run i18n:check`) will fail CI when a language has keys `en` does not, or has `{{placeholders}}` that differ from `en`.

## Phases

**Phase 0: foundation (M1, before new screens are built).**
Install `i18next react-i18next expo-localization` with `npx expo install`; add the `expo-localization` plugin with `supportedLocales: ["en"]` in `app.json`; create `app/src/i18n/` and `lib/format.ts`; move all Home strings into `en` resources; make `data/home.ts` raw values; log a Hermes check that `Intl.PluralRules`, `DateTimeFormat`, `NumberFormat` and `RelativeTimeFormat` work on a real device. Update `getGreeting` to use `t()`.

**Phase 1: settings and API (M1).**
Settings for units, clock and diaper/nappy wording (existing task) read defaults from `getLocales()` / `getCalendars()`. Add `locale` to the user record in the API, send `Accept-Language`, and give Laravel a `lang/` folder (`en` first) for emails, validation messages and push-notification text. The server must send localised push text based on the recipient's locale, not the sender's.

**Phase 2: every feature, M2 to M5.**
Each new screen ships with its strings in `en` resources, passes the rules above and is checked against a pseudo-long-text pass. Nothing new may merge with hard-coded text. Widgets (`expo-widgets`) and Live Activities need their strings from the same resources; plan how they read the locale when we build them in M6.

**Phase 3: first extra languages (M6).**
Order: French, German, Spanish, then Chinese (Simplified). Machine draft, then review by a native-speaking parent. Review pass for tone and for medical wording: translations must keep the "tracks patterns, no medical advice" rule and the honest paywall copy. Localise `app.json` metadata (`locales`, `CFBundleAllowMixedLocalizations`), the App Store and Play Store listings and screenshots, the privacy policy and terms.

## Open items and risks

- **Font coverage:** Outfit covers Latin and most European accents but has **no Chinese glyphs**. Confirm that French and German diacritics render in the bundled `@expo-google-fonts/outfit` weights, and choose the Chinese fallback (system font) before promising `zh-Hans`.
- **Chinese language is not the Chinese market.** Supporting `zh-Hans` for users abroad is cheap. Launching in mainland China needs a separate decision (store requirements, hosting, Pusher availability). Do not assume it.
- **Figma:** add a long-German and a Chinese variant of the key screens (Home, a logging sheet, paywall) to catch truncation before it is built.
- **Date edge cases:** week start day, 24-hour clock and time zones come from the device and baby profile, not from the language.
- **Translation tooling:** decide between plain JSON files in the repo and a service (Crowdin, Lokalise, etc.) when we reach Phase 3; JSON files keep both options open.
